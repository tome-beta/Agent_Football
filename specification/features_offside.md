# オフサイド判定 設計（2026-08-01）

> **実装後の追記**: 当初案（`selectPassReceiver` での完全除外 + `computeTargetPosition` のハードクランプ）は
> どちらも実装したところ、20試合の balance-check で平均得点が導入前の5.00から0.00〜1.05まで
> 急落する強い偏りが発生した。原因の切り分けと実際に採用した設計は本ドキュメント末尾の
> 「実装後の設計変更」を参照。

## 背景

実試合を観察して発見した違和感の原因調査（`anomaly-hunt`/目視確認）より: 「ボールより前方に味方が張り付く」「相手守備がゴール前に戻らない」という不自然な挙動は、オフサイドルールが存在しないことに起因すると判明した。

`features_3_match_rules.md` §7 は当初「3対3では複雑性が低く、オフサイド無しでも十分遊べる」として第一ステップの実装対象外としていたが、実際に試合を観察した結果、非保持時のポジショニング（マイルストーンH）だけでは解消しない不自然さが確認されたため、改めて導入を検討する。

## スコープ（今回導入する範囲）

**ステップ1のみ**: オフサイド判定を選手AIの意思決定（パス受け手選定・受け手ポジショニング）に組み込み、「そもそもオフサイドになるような選択をAIがしない」ことで症状を解消する。**反則としてのルール適用（ターンオーバー処理）は今回のスコープ外**とする。理由: AI回避だけで症状の大部分は解消できる見込みが高く、反則処理を先に入れるとAIが同じ過ちを繰り返して不自然な頻発を招くリスクがある。ステップ1導入後の観察結果を見てステップ2（反則としての実装）に着手するか判断する。

**自陣ハーフルールは省略**: 本来のオフサイドルールには「自陣にいる限りオフサイドにならない」という例外があるが、3対3の狭いピッチでは実効性が薄いため、判定ロジックをシンプルに保つ目的で省略する。

## ルール定義（3vs3・GK無し版）

FIFAの本質: 味方がボールを蹴った瞬間、レシーバーが「相手の最終ライン」と「ボール」より敵ゴール側にいたらオフサイドポジション。GKが存在しない本実装では「後ろから2番目の相手選手」の代わりに、守備側3人のうち自ゴールに一番近い1人を「最終ライン」とする（`features_3_match_rules.md:157` の簡易仕様どおり）。

判定式（Aチーム攻撃方向 +y の場合。Bチームは符号反転）:

```
offsideLine = max(ballPosAtKick.y, lastDefenderY)
isOffside = receiver.pos.y > offsideLine + lineToleranceMeters
```

- `ballPosAtKick`: パスを蹴った瞬間のボール位置（パス実行前の `player.pos`）
- `lastDefenderY`: 守備側チームの中で自ゴールに最も近い（y座標が最も小さい/大きい）選手のy座標
- `lineToleranceMeters`: 「同一ラインならオンサイド」を再現するための許容誤差（config化）

判定対象は**パスのみ**。シュート・ドリブル中の移動・キックオフ/リスタート時の配置は対象外。

## 実装方針

### 新規モジュール: `src/game/offside.ts`

```ts
export function isOffside(
  receiverPos: Vec2,
  side: TeamSide,
  defendingTeam: Team,
  ballPosAtKick: Vec2,
  config: GameConfig
): boolean
```

`attackGoal`/`opposite` 相当の座標系変換は `player.ts` に既存のものがあるため、循環依存にならないよう `offside.ts` 内には座標系変換を持たせず、呼び出し側（`player.ts`）で `side` に応じた符号だけ渡す形にするか、`utils.ts` に共通の座標変換ヘルパーを切り出すかは実装時に判断する。

### 変更1: `selectPassReceiver`（`src/game/player.ts:115`）

パス候補のフィルタ条件に「オフサイドポジションでないこと」を追加する。現状の `marked`（マークされているか）と同様に、オフサイドの候補は `score = -1000` 相当で事実上除外する（候補がゼロになった場合の挙動は既存の「候補なし→ドリブル継続」にそのまま乗る）。

### 変更2: `computeTargetPosition`（`src/game/player.ts:248`）

味方保持/フリーボール時の受け手ポジション算出（284〜300行目）で、算出した `target.y`（攻撃方向）をオフサイドラインでクランプする。これにより「受け手ポジションを狙って動いた結果オフサイドになる」動き自体を予防する。クランプ基準は選手個人ではなく「その瞬間の相手最終ライン」を使う（ボール位置基準ではなく、パスされる保証はないため相手最終ラインのみで判定する簡易版でよい）。

### GameConfig 拡張

```ts
ai: {
  offside: {
    /** オフサイド判定を有効にするか。既存試合バランスとの比較用スイッチ。 */
    enabled: boolean;
    /** 同一ラインとみなす許容誤差 [m]。 */
    lineToleranceMeters: number;
  };
}
```

`src/config/default.ts` にデフォルト値を追加する（`enabled: true`、`lineToleranceMeters` は0.5m程度から balance-check で調整）。

## ステップ2: 反則としてのターンオーバー処理（設計確定・2026-08-03、**実装を試みたが実装は見送り**）

> **実装後の追記（2026-08-03）**: 以下の設計どおり実装し `anomaly-hunt`/`balance-check` で確認したところ、**受け手ポジショニングの設計そのものとオフサイドの反則化が根本的に相性が悪いことが判明し、実装を撤回した**。詳細は本セクション末尾の「実装を試みて判明した根本的な問題」を参照。設計自体は将来受け手ポジショニングを作り直した後の再挑戦のために残す。実際にコミットしたのは `src/game/offside.ts` の `offsideLineY`（オフサイドラインの計算にボール位置も含めるよう整理した副産物）のみで、`Ball.offsideOffenderId` や `handleOffside` などステップ2固有のコードはリポジトリに残っていない。

ステップ1導入後も `avoidChance`（既定0.4）の確率で「あえてオフサイドの選手へパスしてしまう」ケースが残っている。ステップ2はこの見逃しケースを実際の反則として処理する。

### 全体フロー

```
パスを蹴る（decidePossessionAction）
  → 受け手がオフサイドポジションなら Ball.offsideOffenderId にその選手IDをセット
  → ボールは通常どおり Free で飛ぶ（resolveBallPossession は無変更）
  → stepMatch 内の新関数 handleOffside が「フラグの選手が実際に触れたか」を判定
      - フラグの選手が保持者になった → 反則成立。相手ボールで再開（フラグを消す）
      - フラグの選手以外が触れた（味方が拾う/敵がインターセプト） → 不成立。フラグだけ消して通常進行
      - まだ誰も触れていない（Free のまま） → 何もせず次ターンへ持ち越す
```

「オフサイドポジションにいるだけでは反則でない」という実際のルールどおり、フラグは**パスを実行した瞬間だけ**セットする（受け手が動いてオンサイドに戻っても、パスした時点の判定は覆さない。現実のルールも「ボールがプレーされた瞬間」の位置で判定するため整合的）。

### 型の変更

```ts
interface Ball {
  // ...既存
  /** ステップ1で見逃してオフサイドの選手へパスしてしまった場合の一時フラグ。
   *  この選手が実際にボールに触れたら反則が成立する。それ以外の選手が触れたら不成立。 */
  offsideOffenderId: string | null;
}
```

`createBall` は `null` で初期化。`setupKickoff`（キックオフ再配置）・`checkGoal`（得点後リセット）・`handleOutOfBounds`（アウト再開）でも、他のボールフィールドと同様に `null` へ明示的にリセットする（`lastKickerId` とは逆に、新しい局面が始まったら持ち越さない）。

### 実装箇所

- **フラグを立てる場所**: `decidePossessionAction`（`player.ts`）のパス実行分岐。`selectPassReceiver` が既に計算しているオフサイド判定結果をそのまま使い、`kickBall` を呼ぶ直前に `receiver` がオフサイドなら `ball.offsideOffenderId = receiver.id` をセットする（同じ判定を2回計算しない）。
- **反則の成立判定・再開処理**: `match.ts` に `handleOffside(state, config): boolean`（反則が成立したら `true`）を新設し、`checkGoal`/`handleOutOfBounds` と同じ並びで `stepMatch` から呼ぶ。「誰がボールを持っているか」の調停は `resolveBallPossession`（collision.ts）の責務、「ルール上の帰結（得点/反則/アウト）」は `match.ts` の責務、という既存の役割分担に乗せる（`collision.ts` にオフサイドの知識を持ち込まない）。

```
stepMatch の PLAYING 分岐:
  if (!handleOffside(state, config)) {
    if (!checkGoal(state, pitch)) {
      handleOutOfBounds(state, pitch);
    }
  }
```

`handleOffside` を `checkGoal` より先に呼ぶのは、「オフサイドの選手が触れた瞬間」と「ゴール」が理論上同時に起きた場合に反則を優先するため。

### 再開位置・再開権

`handleOutOfBounds` と同型だが、再開位置は**ボールの現在位置**（＝オフサイドの選手が実際に触れた地点）を使う。`handleOutOfBounds` が中央に簡略化しているのと違い、ここは自然に地点情報があるためそのまま使う方が単純かつ現実のインダイレクトフリーキックの位置に近い。

- 資格チーム = 反則した選手の相手チーム
- 再開位置 = ボールの現在位置
- その地点に最も近い資格チームの選手（既存の `nearestPlayerTo` を再利用）に持たせる
- `lastKickerId` は更新しない（キックではないため、既存の奪取処理と同じ扱い）

### Config

新規フラグは追加しない。既存の `config.ai.offside.enabled` で（ステップ1のAI回避＋ステップ2の反則）をまとめてオン/オフする。ただし実装時は一時的に別スイッチを用意し、ステップ1単体とステップ2込みを balance-check で比較してから確定する（ステップ1導入時に段階的な急落を経験しているため、同じ手順で検証する）。

### テスト計画

- `tests/game/match.test.ts`: `handleOffside` の単体テスト（フラグが立った選手が触れたら反則成立・相手ボールで再開／別の選手が触れたら不成立でフラグだけ消える／まだ誰も触れていなければ何もしない）
- `tests/game/player.test.ts`: オフサイドの選手へパスしてしまった場合に `ball.offsideOffenderId` がセットされることを確認
- 導入前後で `balance-check`/`anomaly-hunt` を用いて勝敗分布・試合展開の比較を行う

### 実装を試みて判明した根本的な問題（2026-08-03）

上記設計どおり `Ball.offsideOffenderId` + `handleOffside` を実装し、20シードの `balance-check` で確認したところ、**平均得点数/試合が5.10→1.00**まで急落した。

原因を計測したところ、`avoidChance=0`（一切除外しない）の状態で**パス140回中133回（95%）がオフサイドと判定される**ことが判明した。これは稀な例外ではなく、このAIの標準的な攻撃パターンそのものである。

根本原因は `computeTargetPosition` の受け手ポジション算出ロジック（マイルストーンH）にある。「ボールから攻撃ゴール方向へ `passDistance` の6割ほど進んだ地点」を受け手の目標位置にしているため、受け手は設計上ほぼ常に相手最終ラインより前（＝オフサイドポジション）へ動く。現実のサッカーの「オフサイドラインの裏へ抜け出すランニング」を意図した動きだが、タイミング（オンサイドの状態でスタートして走り込む）の概念がない静的な位置取りモデルのため、パスが来る瞬間は常にオフサイドという構造になっている。

この問題を受け手ポジショニング側で緩和しようと、以下を試みた:

1. **`offsideLineY` の導入**（本セクション冒頭の型どおり、オフサイドラインの計算にボール位置も含めるよう改善）。ただし自然な「95%オフサイド」率はほぼ変化しなかった（依然95%前後）。この改善自体は判定の正確性向上として妥当なため唯一コミットに残した。
2. **`pullWeight`（受け手ポジションをラインへ引き戻すブレンド率）を強める**。0.4/0.6/0.8では自然なオフサイド率がほぼ変化しない（95%→95%→90%）が、**1.0（実質ハードクランプ）にした途端9%まで急落**する強い非線形性を発見した（`interceptDistance` 調整時に見た閾値現象と同種）。しかし `pullWeight=1.0` は当初のハードクランプ実装と同じ「両チームの選手とボールがオフサイドライン付近に団子状に固まって動けなくなる」不安定性を再発させ、平均得点は0.05（19引き分け）まで悪化した。

**結論**: `pullWeight` を弱めると「団子化」は避けられるがオフサイド率95%のままで反則化すると壊滅的、強めると団子化が再発して同じく壊滅的——**この2つの失敗モードの間に許容できる中間点がない**。ブレンド率の調整では解決できず、`computeTargetPosition` の受け手ポジション算出ロジック自体（守備陣形との距離を一切見ない設計）を作り直さない限り、反則化は安全に導入できないと判断し、ステップ2の実装は撤回した。

### ステップ2再挑戦の前提条件（将来着手する場合）

- 受け手ポジショニングを「相手守備陣形からの距離を継続的に考慮する」設計に作り直す（現状の力の合成モデルに新しい力を追加するのではなく、受け手ポジション算出式自体の再設計が必要と見られる）
- 作り直した後、まず「パスの何%が自然にオフサイドになるか」を計測し、十分低い値（目安: 20%未満程度）まで下がることを確認してから反則化に着手する
- 団子化の再発がないか、必ず `anomaly-hunt`/`balance-check` で確認する

## 実装後の設計変更（2026-08-01）

当初案どおり2箇所（`selectPassReceiver` の完全除外、`computeTargetPosition` のハードクランプ）を実装し、`anomaly-hunt` の手順で20シード連続実行して確認したところ、**平均得点数/試合が5.00→0.00（全試合0-0）**という致命的な偏りが発生した。

原因を2段階で切り分けた:

1. **`computeTargetPosition` のハードクランプが支配的要因**: 相手最終ラインを「その瞬間の守備側実位置」から計算するため、既存の `coverBias`/`pressure` により両チームの選手とボールがオフサイドライン付近（y≈5〜7）に団子状に固まって動けなくなるループに陥っていた。クランプを撤去し `selectPassReceiver` フィルタのみに戻しても平均得点は1.05までしか戻らず、まだ大きな偏りが残った。
2. **`selectPassReceiver` の完全除外自体も強すぎた**: このAIにとって「オフサイドポジションぎりぎりの縦パス」が主要な崩し手段になっており、完全に禁止すると代替の崩し方（ドリブル突破等）が育っていないため攻撃全体が機能不全に陥っていた。

**最終的に採用した設計**（当初案から変更）:

- `computeTargetPosition` のクランプは**ハードクランプではなくソフトな引き戻し力**（`config.ai.offside.pullWeight`、0〜1のブレンド率）に変更。ただし20試合比較では pullWeight を0.1〜0.4で振っても平均得点はほぼ変化せず（1.15〜1.35）、主要因ではないと判明。それでも「オフサイドを意識したポジショニング」という設計意図自体は妥当なため残している
- `selectPassReceiver` のオフサイド除外は**完全除外ではなく確率化**（`config.ai.offside.avoidChance`）。0.7/0.4/0.2/0.1 を20試合ずつ比較し、無効時(5.00)に最も近い **`avoidChance=0.4`（平均4.60、勝敗分布も無効時に近い）** を採用
- `GameConfig.ai.offside` は最終的に `enabled` / `lineToleranceMeters` / `pullWeight` / `avoidChance` の4項目

この経緯から得られる教訓: 意思決定側（パス判定）とポジショニング側（受け手の動き）のどちらか一方だけをルール認識させると、もう一方が無頓着なまま動き続けるため机上の想定より遥かに強い副作用が出る。また「ルールを完全に禁止として実装する」より「役割ロール分岐にせず確率・重みで表現する」という本プロジェクトの既存方針（開発メモ参照）が、オフサイドのような新ルール導入でも有効だった。
