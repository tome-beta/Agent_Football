# オフサイド判定 設計（2026-08-01）

> **実装後の追記**: 当初案（`selectPassReceiver` での完全除外 + `computeTargetPosition` のハードクランプ）は
> どちらも実装したところ、20試合の balance-check で平均得点が導入前の5.00から0.00〜1.05まで
> 急落する強い偏りが発生した。原因の切り分けと実際に採用した設計は本ドキュメント末尾の
> 「実装後の設計変更」を参照。

## 背景

実試合を観察して発見した違和感の原因調査（`anomaly-hunt`/目視確認）より: 「ボールより前方に味方が張り付く」「相手守備がゴール前に戻らない」という不自然な挙動は、オフサイドルールが存在しないことに起因すると判明した。

`features_3_match_rules.md` §7 は当初「3対3では複雑性が低く、オフサイド無しでも十分遊べる」として第一ステップの実装対象外としていたが、実際に試合を観察した結果、非保持時のポジショニング（マイルストーンH）だけでは解消しない不自然さが確認されたため、改めて導入を検討する。

## スコープ（今回導入する範囲）

**ステップ1のみ**: オフサイド判定を選手AIの意思決定（パス受け手選定・受け手ポジショニング）に組み込み、「そもそもオフサイドになるような選択をAIがしない」ことで症状を解消する。**反則としてのルール適用（ターンオーバー処理）は今回のスコープ外**とする。理由: AI回避だけで症状の大部分は解消できる見込みが高く、反則処理を先に入れるとAIが同じ過ちを繰り返して不自然な頻発を招くリスクがある。ステップ1導入後の観察結果を見てステップ2（反則としての実装）に着手するか判断する。

**自陣ハーフルールは省略**: 本来のオフサイドルールには「自陣にいる限りオフサイドにならない」という例外があるが、3対3の狭いピッチでは実効性が薄いため、判定ロジックをシンプルに保つ目的で省略する。

## ルール定義（3vs3・GK無し版）

FIFAの本質: 味方がボールを蹴った瞬間、レシーバーが「相手の最終ライン」と「ボール」より敵ゴール側にいたらオフサイドポジション。GKが存在しない本実装では「後ろから2番目の相手選手」の代わりに、守備側3人のうち自ゴールに一番近い1人を「最終ライン」とする（`features_3_match_rules.md:157` の簡易仕様どおり）。

判定式（Aチーム攻撃方向 +y の場合。Bチームは符号反転）:

```
offsideLine = max(ballPosAtKick.y, lastDefenderY)
isOffside = receiver.pos.y > offsideLine + lineToleranceMeters
```

- `ballPosAtKick`: パスを蹴った瞬間のボール位置（パス実行前の `player.pos`）
- `lastDefenderY`: 守備側チームの中で自ゴールに最も近い（y座標が最も小さい/大きい）選手のy座標
- `lineToleranceMeters`: 「同一ラインならオンサイド」を再現するための許容誤差（config化）

判定対象は**パスのみ**。シュート・ドリブル中の移動・キックオフ/リスタート時の配置は対象外。

## 実装方針

### 新規モジュール: `src/game/offside.ts`

```ts
export function isOffside(
  receiverPos: Vec2,
  side: TeamSide,
  defendingTeam: Team,
  ballPosAtKick: Vec2,
  config: GameConfig
): boolean
```

`attackGoal`/`opposite` 相当の座標系変換は `player.ts` に既存のものがあるため、循環依存にならないよう `offside.ts` 内には座標系変換を持たせず、呼び出し側（`player.ts`）で `side` に応じた符号だけ渡す形にするか、`utils.ts` に共通の座標変換ヘルパーを切り出すかは実装時に判断する。

### 変更1: `selectPassReceiver`（`src/game/player.ts:115`）

パス候補のフィルタ条件に「オフサイドポジションでないこと」を追加する。現状の `marked`（マークされているか）と同様に、オフサイドの候補は `score = -1000` 相当で事実上除外する（候補がゼロになった場合の挙動は既存の「候補なし→ドリブル継続」にそのまま乗る）。

### 変更2: `computeTargetPosition`（`src/game/player.ts:248`）

味方保持/フリーボール時の受け手ポジション算出（284〜300行目）で、算出した `target.y`（攻撃方向）をオフサイドラインでクランプする。これにより「受け手ポジションを狙って動いた結果オフサイドになる」動き自体を予防する。クランプ基準は選手個人ではなく「その瞬間の相手最終ライン」を使う（ボール位置基準ではなく、パスされる保証はないため相手最終ラインのみで判定する簡易版でよい）。

### GameConfig 拡張

```ts
ai: {
  offside: {
    /** オフサイド判定を有効にするか。既存試合バランスとの比較用スイッチ。 */
    enabled: boolean;
    /** 同一ラインとみなす許容誤差 [m]。 */
    lineToleranceMeters: number;
  };
}
```

`src/config/default.ts` にデフォルト値を追加する（`enabled: true`、`lineToleranceMeters` は0.5m程度から balance-check で調整）。

## テスト計画

- `tests/game/offside.test.ts`: `isOffside` の単体テスト
  - 相手最終ラインより後ろ → オンサイド
  - 相手最終ラインより前、ボールより後ろ → オンサイド（ボール基準が効くケース）
  - 相手最終ラインとボールの両方より前 → オフサイド
  - 許容誤差ちょうど（境界値）→ オンサイド
  - A/B両チームで攻撃方向反転が正しく効くこと
- `tests/game/player.test.ts`: `selectPassReceiver` がオフサイドポジションの候補を除外すること
- 導入前後で `balance-check`/`anomaly-hunt` を用いて勝敗分布・試合展開の比較を行う

## 実装後の設計変更（2026-08-01）

当初案どおり2箇所（`selectPassReceiver` の完全除外、`computeTargetPosition` のハードクランプ）を実装し、`anomaly-hunt` の手順で20シード連続実行して確認したところ、**平均得点数/試合が5.00→0.00（全試合0-0）**という致命的な偏りが発生した。

原因を2段階で切り分けた:

1. **`computeTargetPosition` のハードクランプが支配的要因**: 相手最終ラインを「その瞬間の守備側実位置」から計算するため、既存の `coverBias`/`pressure` により両チームの選手とボールがオフサイドライン付近（y≈5〜7）に団子状に固まって動けなくなるループに陥っていた。クランプを撤去し `selectPassReceiver` フィルタのみに戻しても平均得点は1.05までしか戻らず、まだ大きな偏りが残った。
2. **`selectPassReceiver` の完全除外自体も強すぎた**: このAIにとって「オフサイドポジションぎりぎりの縦パス」が主要な崩し手段になっており、完全に禁止すると代替の崩し方（ドリブル突破等）が育っていないため攻撃全体が機能不全に陥っていた。

**最終的に採用した設計**（当初案から変更）:

- `computeTargetPosition` のクランプは**ハードクランプではなくソフトな引き戻し力**（`config.ai.offside.pullWeight`、0〜1のブレンド率）に変更。ただし20試合比較では pullWeight を0.1〜0.4で振っても平均得点はほぼ変化せず（1.15〜1.35）、主要因ではないと判明。それでも「オフサイドを意識したポジショニング」という設計意図自体は妥当なため残している
- `selectPassReceiver` のオフサイド除外は**完全除外ではなく確率化**（`config.ai.offside.avoidChance`）。0.7/0.4/0.2/0.1 を20試合ずつ比較し、無効時(5.00)に最も近い **`avoidChance=0.4`（平均4.60、勝敗分布も無効時に近い）** を採用
- `GameConfig.ai.offside` は最終的に `enabled` / `lineToleranceMeters` / `pullWeight` / `avoidChance` の4項目

この経緯から得られる教訓: 意思決定側（パス判定）とポジショニング側（受け手の動き）のどちらか一方だけをルール認識させると、もう一方が無頓着なまま動き続けるため机上の想定より遥かに強い副作用が出る。また「ルールを完全に禁止として実装する」より「役割ロール分岐にせず確率・重みで表現する」という本プロジェクトの既存方針（開発メモ参照）が、オフサイドのような新ルール導入でも有効だった。
