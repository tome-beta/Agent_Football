# 受け手ポジショニング再設計 手法候補（2026-08-04）

## 背景

`specification/features_offside.md`「マイルストーンJ」でオフサイドの反則化を試みた際、`computeTargetPosition`（`src/game/player.ts`）の受け手ポジション算出ロジックが「ボールから攻撃ゴール方向へ固定距離だけ進んだ地点」を目標にする単一の式になっており、これが以下の板挟みを引き起こすことが判明した。

- 弱いソフト補正（`pullWeight`低）→ 自然な状態でパスの95%がオフサイドと判定される
- 強い補正（`pullWeight`≈1、実質ハードクランプ）→ 相手最終ラインを毎ターンの実位置から計算しているため、味方のポジショニングと相手の守備（`coverBias`/`pressure`）が互いに反応し合うフィードバックループに陥り、両チームがボール付近に団子状に固まって動けなくなる（平均得点0.05まで悪化）

「単一の目標地点を先に決め打ちし、あとからオフサイドラインで事後パッチする」という現在の構造そのものが問題であり、ブレンド率の調整では解決できないと判断した。

この問題を調べる過程で、サッカー分析（Pitch Control）と将棋AI（KPP評価関数）の先行研究を参照した。両者に共通するのは「単一の決め打ち計算」ではなく「複数の関係性・到達可能性を総合して評価する」という発想であり、受け手ポジショニングの再設計にも応用できると考えられる。

## 参考にした先行研究

- **Pitch Control**（William Spearman）: 距離ではなく「到達時間」を軸に、各選手がその地点を制御できる確率を計算する空間支配モデル。ボロノイ分割・不確実性の導入などフル実装は重いが、「到達時間で優劣を決める」という考え方自体は軽量に取り入れられる
- **Offside Control**（2025年の追試論文）: Pitch Controlをオフサイドラインの評価に応用した直接の先行研究。攻撃側がオフサイドライン先にどれだけ脅威を作れているか、守備側がどれだけリスクを負っているかを定量化する
- **将棋AI の KPP 評価関数**（Bonanzaメソッド、保木邦仁 2006）: 局面全体の評価値を「玉+駒+駒」の3駒関係ごとのスコアの総和で計算する。単一の式で盤面を評価するのではなく、ペアワイズな関係性を足し合わせる設計
- **RoboCupシミュレーションリーグ**: ポテンシャルフィールド・ボロノイ図を使った戦略的ポジショニングが標準的に使われている。本プロジェクトのマイルストーンH（力の合成モデル）と同系統のアプローチ

（各文献の詳細URLは会話ログ参照。本ドキュメントでは設計への示唆のみ記載する）

## 手法候補

以下、リスク・実装コストの低い順に並べる。

### 方式A: 前進距離の静的キャップ（フィードバックループ根絶）

相手の生の位置を一切参照せず、「ボールから攻撃ゴールまでの残り距離」という自チームの状況だけで前進上限を決める。

```
maxForwardReach = min(
  passDistance * receivingDistanceFactor,               // 既存のパス圏内という制約
  (attackGoalY - ballAdvancementY) * forwardFraction     // 新規: 残り距離の一定割合
)
```

- **利点**: 相手の動きに反応しないため、団子化の温床である相互フィードバックループが構造的に発生しない。実装コストが最小（既存の `receivingDistance` 計算に `Math.min` を1つ足すだけ）
- **欠点**: 「相手が実際に高いラインを敷いているか」を見ていないため、オフサイド回避としての近似精度は低い。相手が低いラインを引いている場面でも保守的になりすぎる可能性がある
- **リスク**: 低。既存アーキテクチャへの変更が最小で、`balance-check` での検証も素早く回せる

### 方式B: 低域通過フィルタで相手ラインを平滑化

現行方式（`offsideLineY` を毎ターン参照してソフトプル）は維持しつつ、参照する「相手最終ライン」だけを毎ターンの生値ではなく指数移動平均（EMA）で滑らかにする。

```
GameState に smoothedOffsideLineY: { A: number; B: number } を追加
毎ターン: smoothedLineY += (liveLineY - smoothedLineY) * smoothingRate
```

- **利点**: 相手が一瞬だけ前に出たことに過剰反応せず、系がゆっくり追従するためフィードバックループの発振が抑えられる可能性がある。既存の `pullWeight` の仕組みをそのまま流用できる
- **欠点**: `GameState` に新しいステートを追加する必要があり（`step*` 系は基本ステートレスな計算が多いので設計上の異物になりやすい）、`smoothingRate` という新しいハイパーパラメータの調整が必要。根本原因（単一の目標地点を先に決めて後からパッチする構造）自体は変わらないため、効果が読みにくい
- **リスク**: 中。新しいstateとパラメータの組み合わせで、また別の非線形現象が出る可能性がある

### 方式C: 到達時間ベースの簡易Pitch Control

候補地点ごとに「相手DFのうち最も早くそこへ到達できる選手」と「自分がそこへ到達する時間」を比較し、自分が優位（相手より速く/同時に到達できる）な地点だけを候補にする。

```
候補地点 p について:
  myArrivalTime = distance(player.pos, p) / effectiveSpeed(player, config)
  oppArrivalTime = min(defendingTeam.players.map(d => distance(d.pos, p) / effectiveSpeed(d, config)))
  isSafe = myArrivalTime <= oppArrivalTime + safetyMarginSeconds
```

- **利点**: Spearman の pitch control の本質（距離でなく到達時間）を取り入れるため、選手ごとの `speed` パラメータが初めてポジショニングの意思決定に反映される（現状 `speed` は移動速度にしか使われていない）。相手が遅ければ深く攻め込め、速ければ慎重になるという、より現実的な振る舞いが自然に出る
- **欠点**: 候補地点をサンプリングする必要があり（方式Dと組み合わせるのが自然）、計算コストが単一式より増える（3対3なので実害は小さいはず）
- **リスク**: 中。新しい評価軸なので、既存のオフサイド回避・受け手選択ロジックとの相互作用を `balance-check` で丁寧に見る必要がある

### 方式D: 候補点サンプリング＋KPP的な関係性スコアリング

ボール周辺〜攻撃方向にいくつか候補地点をサンプリングし、各候補を「相手選手ごと・味方選手ごと・ゴール・ボールとの関係」の重み付き総和でスコアリングして最良点を選ぶ。方式Cの「到達時間の安全性」もこの枠組みの1項目として組み込める。

```
score(p) = Σ_defender safetyTerm(p, defender)      // 方式Cの安全性を項の1つとして使える
         + Σ_teammate spacingTerm(p, teammate)      // 既存の teammateRepulsion を統合
         + goalProximityTerm(p)
         + passReachabilityTerm(p, ball)

target = argmax_p score(p)
```

- **利点**: 4案の中で最も表現力が高く、「団子化」「オフサイド」「パスコース」「フォーメーション」を単一の統一された枠組みで同時に扱える。既存の力の合成方針（役割分岐せず重みの総和で表現する。`specification/開発メモ.md` 参照）とも最も親和性が高い
- **欠点**: 実装コストが最も高い（候補点サンプリング戦略・各項の重みという新しい調整対象が多数増える）。パラメータ数が増えるほど、以前発見した非線形な閾値現象の起きる箇所も増える可能性がある
- **リスク**: 高。ただし1つ1つの項をこれまでの `balance-check` 手法で段階的に検証していけば制御可能

## 推奨する進め方

リスクの低い順に **A → C → D** と段階的に組み込むのが安全。

1. まず方式A（静的キャップ）だけを入れ、団子化が起きないか・自然なオフサイド率がどこまで下がるかを `anomaly-hunt`/`balance-check` で確認する
2. それでもオフサイド率が高すぎる（目安: 20%超）なら方式C（到達時間ベースの安全性判定）を追加する
3. それでも表現力が足りなければ方式D（KPP的スコアリング）へ拡張し、C はDの一項目として統合する

方式Bは根本原因（単一目標地点の事後パッチという構造）を解決しないため、優先度を下げる。

## 方式A 実装結果（2026-08-04）

`GameConfig.ai.offside.forwardReachFraction` として実装した（`src/game/player.ts` の受け手ポジション算出、`config.ai.offside.enabled` 時のみ有効）。`forwardReachFraction`（0.05〜1.0）を振って `balance-check`（20シード）と自然なオフサイド率（`avoidChance=0`での計測）を確認した。

| `forwardReachFraction` | 自然なオフサイド率 | 平均得点/試合 |
|---|---|---|
| 0.05 | 87% | 2.40 |
| 0.1 | 84% | 3.80 |
| 0.15 | 76% | 4.40 |
| 0.2 | 75% | 4.65 |
| **0.3（採用）** | **68%** | **4.55** |
| 0.5 | 73% | 5.05 |
| 0.6 | 70% | 4.25 |
| 0.8 | 70% | 4.90 |
| 1.0 | 69% | 4.30 |

**得られた知見**:
- 想定どおり、方式Aは相手の実位置を参照しないため**団子化は0.05〜1.0の全域で一度も再発しなかった**（平均得点は常に2.40〜5.05の範囲に収まり、ステップ2で見た0.05のような壊滅的な崩壊はない）
- 自然なオフサイド率は **95%→68%**（`avoidChance=0`時点）まで改善したが、**0.2以下までさらに絞ると逆に悪化する**（オフサイド率75%超・得点も低下）という非単調な挙動を発見した。上限を絞りすぎると受け手がボールのすぐそばに滞留し、かえって密集を招くためと考えられる
- 68%は依然として「再挑戦の前提条件」で定めた目安（20%未満）に届いていない。**方式A単独では不十分**という設計時の想定どおりの結果になった

## 方式C 実装結果（2026-08-05）

`safeForwardDistance`（`src/game/player.ts`）として実装した。方式Aで求めた上限距離を、ボール→ゴール方向の直線上で`arrivalSampleSteps`段階（既定8）サンプリングし、「自分の到達時間（`distance/effectiveSpeed`） <= 相手DF最速到達者の到達時間 + `arrivalSafetyMarginSeconds`」を満たす最も前進した距離を選ぶ。方式Aの上限内でのみ絞り込むため、方式Aが保証する「団子化しない」という性質を壊さない設計にした。

`arrivalSafetyMarginSeconds`（-0.5〜0.2）を振って `balance-check`（20シード）と自然なオフサイド率を確認した。

| `arrivalSafetyMarginSeconds` | 自然なオフサイド率 | 平均得点/試合 |
|---|---|---|
| -0.5 | 4% | 0.40 |
| -0.2 | 14% | 1.25 |
| -0.15 | 33% | 2.60 |
| -0.1 | 42% | 2.80 |
| -0.05 | 54% | 3.80 |
| **0（採用）** | **59%** | **4.45** |
| 0.2 | 65% | 4.95 |

**得られた知見**:
- 方式Bやステップ2のハードクランプで見た「非線形な閾値による完全崩壊」（0.00〜0.05まで落ちる）は**再発しなかった**。マージンを絞るほどオフサイド率と得点がなめらかに連動して低下する、素直なトレードオフ曲線になっている。方式Aの安全な上限内でのみ相手位置を参照する、という設計上の制約が効いていると考えられる
- `margin=0`（採用値）で追加の得点コストなしに、方式A単独の68%から**59%**まで改善した
- 目標（20%未満）に届かせるには`margin≈-0.2`まで絞る必要があるが、そこでは平均得点が1.25まで下がる。目標未達成のままだが、これは「団子化」のような不具合ではなく、素直に守備が堅くなりすぎているだけなので、目標値自体をどう扱うかはユーザー判断で保留とした

**次のステップ**: 目標の20%未満に届いていないため、方式D（KPP的な候補点スコアリング）で表現力を上げるか、あるいは59%という現状の改善幅で一旦ステップ2（反則化）に再挑戦してみるかを検討する。

（実際には2026-08-05にユーザー指示で先にステップ2への再挑戦を行い、方式A・C止まりの59%のままでも同じ破滅的偏りが再現することを確認した。結果は `specification/features_offside.md`「再挑戦（2026-08-05）」を参照。その後2026-08-06に方式Dへ着手した。）

## 方式D 実装結果（2026-08-06）

`selectReceivingDistance`（`src/game/player.ts`）として実装した。方式A（`forwardReachFraction`）で求めた前進上限内をサンプリングする点は方式Cと同じだが、「安全な地点を見つけたら確定」という閾値カットオフではなく、候補ごとに次の3項の重み付き総和でスコアリングし argmax を選ぶ点が異なる。

```
score(d) = kpp.forwardWeight * (前進度 0〜1)
         - kpp.offsideOvershootWeight * (オフサイドライン超過量[m])
         - kpp.arrivalDeficitWeight * (相手DF最速到達者への到達時間の遅れ[秒])
```

方式Cにあった `pullWeight`（事後のソフトクランプ）は廃止し、オフサイド超過への連続的なペナルティに統合した。

**測定結果**:
- `offsideOvershootWeight` を2→32まで強めても、自然なオフサイド率（`avoidChance=0`時点）は60%→51%程度で頭打ちになり、方式A+C単独（59%）からほとんど改善しなかった
- 実際にステップ2の反則を有効化した状態の20シードbalance-checkでは、重みの組み合わせを変えても平均得点0.30〜0.40点/試合で、方式A+C単独導入時（0.45点/試合）と同水準の壊滅的な偏りから抜け出せなかった
- 一方で、方式B/ステップ2のハードクランプで見られた「非線形な閾値による完全崩壊」（0.00〜0.05まで落ちる団子化）は再発しなかった。単一のargmaxで滑らかにスコアリングする設計が、少なくとも団子化という失敗モードには効いていることがわかる

**原因の見立て**: `computeTargetPosition`（安全な狙い所を計算する側）をいくら精緻化しても、実際に誰にパスするかを決める `selectPassReceiver` は完全に独立したロジック（マーク有無とゴール距離のみ）で動いており、両者が連動していない。さらに選手は毎ターン `speed` 上限付きで目標へ近づくだけなので、守備ラインが動くたびに追従が遅れる。「狙う場所」だけを賢くしても、「実際に選ばれる受け手」や「そこへ到達するまでの遅れ」という別の変動要因が支配的なため、根本的な改善に至らなかったと考えられる。

**結論**: 方式Dはコード（`config.ai.offside.kpp`、`enabled: false` のままリポジトリに残置）としては団子化を再発させない改善だが、自然なオフサイド率・反則化時の得点崩壊のどちらも方式A+Cから実質的に前進しなかった。目標達成には `selectPassReceiver` と `computeTargetPosition` を統合する、より大掛かりな再設計が必要と判断し、2026-08-06時点でここまでの検証を打ち切った。

## 方式E 実装結果（2026-08-06〜07、統一スコアリング）

方式Dの原因分析（`selectPassReceiver` と `computeTargetPosition` が別々のスコア関数で動いている）を受け、両者が共有する単一のスコア関数 `scoreReceivingSpot`（`src/game/player.ts`）を新設した。

```
scoreReceivingSpot(pos) = kpp.forwardWeight * (前進度 0〜1)
                         - kpp.offsideOvershootWeight * (オフサイドライン超過量[m])
                         - kpp.markingWeight * (マーク圧力: 最近接敵との距離が近いほど増加)
```

- `selectPassReceiver` は旧来の `(marked ? -1000 : 0) - distToGoal` を撤去し、`enabled: true` 時はこの共有スコアで候補をランキングする（`avoidChance` による確率的除外も撤去。設定フィールド自体を削除した）
- `computeTargetPosition` の受け手ポジション算出（旧 方式D `selectReceivingDistance`）も、共有スコア + 個人固有の到達時間項（`kpp.arrivalDeficitWeight`、方式C由来）で候補地点をargmax選択するよう書き換えた
- `enabled: false` のデフォルト動作は変更していない（headless実行のスコア傾向は導入前と同一）

**測定結果（`offsideOvershootWeight` を2→200で比較、20シード）**:

| `offsideOvershootWeight` | 自然なオフサイド率 | 平均得点/試合（反則有効時） |
|---|---|---|
| 2 | 46.8% | 0.55 |
| 4 | 28.4% | - |
| 8 | 23.0% | 0.15 |
| **16** | **19.3%** | **0.10** |
| 32 | 18.6% | 0.30 |
| 64 | 18.3% | 0.30 |
| 200 | 18.5% | 0.15 |

**得られた知見**:
- 統一スコアリングは診断どおり効き、自然なオフサイド率は方式Dの51%止まりから**16〜18%台まで下がり、初めて「20%未満」の目標を達成した**
- ところが目標達成後も反則有効化時の平均得点は0.10〜0.55点/試合のままで、**方式Dと同水準の壊滅的な偏りから一切改善しなかった**。`offsideOvershootWeight`をさらに極端（200）にしても変化なし
- **「反則の再開ルール（位置）が原因では」という仮説を実験で検証した**: `handleOffside` の再開地点を実際のオフサイド地点ではなく常にピッチ中央に変える一時的な改造を行い同条件で再測定したところ、平均得点は0.10→0.50とわずかに改善しただけで、依然壊滅的な水準のままだった（検証後は即座に元の実装へ戻した。コミットには含まれていない）。座標系上、Aチームがオフサイドになる地点はBチーム自身の守備エリアに当たるため、Bが得るボールは「攻撃側への贈り物」ではなく実質的な「クリア」に近い位置であり、再開位置は主要因ではないと判断した

**現時点の結論**: 「自然なオフサイド率を20%未満にすれば安全」という、マイルストーンK以来の前提条件そのものが誤りだった可能性が高い。真の原因は再開ルールの位置ではなく、**このAIの攻撃がほぼ縦パスに依存しており（`specification/開発メモ.md`参照）、ドリブル等の代替手段が弱いため、20%弱の頻度で縦パスが完全なターンオーバーになるだけでも攻撃全体が機能不全に陥る**という、受け手ポジショニングの外側にある構造的な脆さだと考えられる（`avoidChance=0.7`で得点5.00→3.65に落ちた過去の実験と同じ力学）。受け手ポジショニング側の改善（方式A〜E）はここでいったん打ち切り、`config.ai.offside.enabled` は `false` のまま維持する。再挑戦するなら、ポジショニングではなく攻撃側の選択肢（ドリブル・短いパスなどの代替ルート）を強化するか、反則発生率を一桁台まで下げる別のアプローチが必要。

## この設計を実装する際の注意点（過去の失敗から）

- 新しいパラメータを追加したら、必ず `balance-check` で複数の値を比較してから既定値を決める（`pullWeight`/`avoidChance` で経験した非線形な閾値現象が別の箇所でも起こりうる）
- 「自然な状態でのオフサイド率」のような診断用の計測スクリプト（`anomaly-hunt` 参照）を先に用意し、変更のたびに計測して回帰を早期発見する
- 受け手ポジショニングを変更したら、既存のパス選択（`selectPassReceiver`）・ドリブル選択（`dribbleChanceBase` 系）との相互作用も含めて `balance-check` する（今回、受け手ポジションを変えると攻撃全体の得点力が大きく揺れることが繰り返し確認されている）
