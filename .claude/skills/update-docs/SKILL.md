# ドキュメント更新スキル

## いつ使うか

- マイルストーン（`TODO.md` の A〜H など）の項目を完了させたとき
- `GameConfig` に新しいキーを追加した、型や関数のシグネチャを変えた、レイヤー構成を変えたとき
- ユーザーから「ドキュメント更新して」「TODO直して」と明示的に頼まれたとき
- 一連の実装作業が一段落し、`TODO.md`/`README.md`/`docs/` の記述が今の `src/` の状態と食い違っていそうだと気づいたとき

## 更新対象と役割分担

このプロジェクトのドキュメントはそれぞれ役割が違う。**全部を毎回機械的に触るのではなく、変更内容に応じて必要なものだけ更新する**こと。

| ファイル | 役割 | 更新するタイミング |
|---|---|---|
| `TODO.md` | マイルストーンの進捗チェックリスト。各項目に「何を・どう実装したか」を一言添える形式 | 実装したタスクの `- [ ]` を `- [x]` にし、実装内容・関連ファイル・見つかった問題点を追記するとき |
| `README.md` | プロジェクト全体のステータスサマリ（概要・実装済み機能一覧・ディレクトリ構成） | マイルストーン完了、ステータス行（「マイルストーンA〜H 完了」等）や実装済み機能一覧が古くなったとき、`src/` にファイル追加・削除があってディレクトリ構成が変わったとき |
| `docs/api.md` | 型・関数のリファレンス | `src/types.ts` の型や `src/game/*` などの公開関数のシグネチャ・挙動が変わったとき |
| `docs/architecture.md` | 層構成・依存関係・データフロー | レイヤー間の依存関係やモジュール構成そのものが変わったとき（頻度は低い） |
| `docs/development_guide.md` | 開発時の実務的なガイド（コマンド・テスト配置規約など） | コマンドやテスト規約、開発フローが変わったとき |
| `CLAUDE.md` | Claude Code 向けの恒久的な規約・アーキテクチャ説明 | プロジェクトの設計原則・約束事そのものが変わったとき（滅多にない。安易に触らない） |
| `specification/*.md` | 設計意図のドキュメント（背景・なぜそうするか） | 通常は更新しない。実装がここに書かれた設計意図と意図的に異なる選択をした場合のみ `TODO.md` の「`specification/` と実装の既知の差分」セクションに追記する（`specification/*.md` 自体は書き換えない） |

## 手順

1. **何が変わったかを確認する**: 直近の実装内容（会話の文脈・`git diff`・`git log`）を振り返り、上の表に沿ってどのドキュメントが影響を受けるか判断する。
2. **`TODO.md` を先に更新する**: 該当項目を `- [x]` にし、既存の記述スタイル（「〜を実装 `モジュール名` — 具体的に何をしたか、関連する関数名・テストファイル名」）に合わせて一言添える。新しいマイルストーンを丸ごと追加する場合は既存の見出し階層（`### マイルストーンX: 見出し ✅ 完了`）を踏襲する。
3. **`README.md` のステータスを合わせる**: 「概要」セクションのステータス行・実装済み機能一覧が `TODO.md` の完了状況と矛盾していないか確認し、必要なら書き直す。ディレクトリ構成のコードブロックも `src/` の実際の構成とズレていたら直す。
4. **`docs/api.md` / `docs/architecture.md` / `docs/development_guide.md`**: 型定義・関数・コマンド・依存関係が変わっていれば該当箇所だけピンポイントで直す。実装が正、ドキュメントを実装に合わせる（`CLAUDE.md` の方針どおり）。
5. **矛盾チェック**: 更新後、以下を grep や目視で確認する。
   - 具体的な数値（テスト件数、勝敗分布、スコア例など）が最新の実行結果と食い違っていないか
   - 日付表記が実際の作業日と合っているか（`YYYY-MM-DD` 形式、会話中の `currentDate` を使う）
   - `TODO.md` 内で完了マイルストーンの直後にある「推奨着手順」「第二ステップ以降」などのセクションが古い前提のままになっていないか
6. **`specification/` は基本的に読むだけ**: 実装との差分は `TODO.md` 側に記録する。设計意図そのものを書き換えたい場合はユーザーに確認してから行う。

## 書き方のトーン

- 既存ドキュメントは日本語・である体/常体混在だが簡潔。過度に丁寧な文体にしない。
- 「なぜその実装を選んだか」「何を発見したか」を一言残す（例: 「〜という偏りを発見し、〜で対処」）。単に「実装した」だけで終わらせない。
- 見出し番号・マイルストーン名（A〜H）は勝手に増やしたり順番を変えたりしない。次のマイルストーンを追加する場合はユーザーと相談する。
