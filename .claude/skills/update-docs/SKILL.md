# ドキュメント更新スキル

## いつ使うか

- マイルストーン（`TODO.md` の A〜H など）の項目を完了させたとき
- `GameConfig` に新しいキーを追加した、型や関数のシグネチャを変えた、レイヤー構成を変えたとき
- ユーザーから「ドキュメント更新して」「TODO直して」と明示的に頼まれたとき
- 一連の実装作業が一段落し、`TODO.md`/`README.md`/`docs/` の記述が今の `src/` の状態と食い違っていそうだと気づいたとき

## 更新対象と役割分担

このプロジェクトのドキュメントはそれぞれ役割が違う。**全部を毎回機械的に触るのではなく、変更内容に応じて必要なものだけ更新する**こと。

`TODO.md` は2026-08-11 に再編され、**進捗チェックリストの詳細は `TODO_ARCHIVE.md` に切り出し済み**。`TODO.md` 自体は「全体方針」「現在の到達点（要約）」「未完了タスク」だけを持つ薄いサマリになっている。

| ファイル | 役割 | 更新するタイミング |
|---|---|---|
| `TODO.md` | 現在地の要約と**未完了タスクのみ**の一覧（完了済みの詳細は持たない） | タスクが完了したとき: 「未完了タスク」から該当項目を削除し、「現在の到達点」の要約を1〜2行更新する。新しいマイルストーンに着手するときは「未完了タスク」に追記する |
| `TODO_ARCHIVE.md` | 完了・撤回済みマイルストーンの詳細記録（「何を・どう実装したか」「何を発見したか」を1項目ずつ残す形式） | タスクを完了させたとき: 該当マイルストーンの `- [ ]` を `- [x]` にし、既存の記述スタイル（「〜を実装 `モジュール名` — 具体的に何をしたか、関連する関数名・テストファイル名」）に合わせて一言添える。新しいマイルストーンを丸ごと完了させた場合はこのファイルに見出し（`### マイルストーンX: 見出し ✅ 完了`）ごと追記し、`TODO.md` 側は要約1行に留める |
| `README.md` | プロジェクト全体のステータスサマリ（概要・実装済み機能一覧・ディレクトリ構成） | マイルストーン完了、ステータス行（「マイルストーンA〜M 完了/決着済み」等）や実装済み機能一覧が古くなったとき、`src/` にファイル追加・削除があってディレクトリ構成が変わったとき |
| `docs/api.md` | 型・関数のリファレンス | `src/types.ts` の型や `src/game/*` などの公開関数のシグネチャ・挙動が変わったとき |
| `docs/architecture.md` | 層構成・依存関係・データフロー | レイヤー間の依存関係やモジュール構成そのものが変わったとき（頻度は低い） |
| `docs/development_guide.md` | 開発時の実務的なガイド（コマンド・テスト配置規約など） | コマンドやテスト規約、開発フローが変わったとき |
| `CLAUDE.md` | Claude Code 向けの恒久的な規約・アーキテクチャ説明 | プロジェクトの設計原則・約束事そのものが変わったとき（滅多にない。安易に触らない） |
| `specification/*.md` | 設計意図のドキュメント（背景・なぜそうするか） | 通常は更新しない。実装がここに書かれた設計意図と意図的に異なる選択をした場合のみ `TODO_ARCHIVE.md`（または現在進行中のタスクなら `TODO.md`）の「`specification/` と実装の既知の差分」セクションに追記する（`specification/*.md` 自体は書き換えない） |

## 手順

1. **何が変わったかを確認する**: 直近の実装内容（会話の文脈・`git diff`・`git log`）を振り返り、上の表に沿ってどのドキュメントが影響を受けるか判断する。
2. **`TODO_ARCHIVE.md`/`TODO.md` を先に更新する**: 完了したタスクの詳細（実装内容・関連ファイル・発見した問題点）は `TODO_ARCHIVE.md` に1項目ずつ残し、`TODO.md` 側は「未完了タスク」からその項目を消して「現在の到達点」の要約を更新するだけにする。両方に同じ詳細を重複させない。
3. **`README.md` のステータスを合わせる**: 「概要」セクションのステータス行・実装済み機能一覧が `TODO.md`/`TODO_ARCHIVE.md` の完了状況と矛盾していないか確認し、必要なら書き直す。ディレクトリ構成のコードブロックも `src/` の実際の構成とズレていたら直す。
4. **`docs/api.md` / `docs/architecture.md` / `docs/development_guide.md`**: 型定義・関数・コマンド・依存関係が変わっていれば該当箇所だけピンポイントで直す。実装が正、ドキュメントを実装に合わせる（`CLAUDE.md` の方針どおり）。
5. **矛盾チェック**: 更新後、以下を grep や目視で確認する。
   - 具体的な数値（テスト件数、勝敗分布、スコア例など）が最新の実行結果と食い違っていないか
   - 日付表記が実際の作業日と合っているか（`YYYY-MM-DD` 形式、会話中の `currentDate` を使う）
   - `TODO.md` の「未完了タスク」が古い前提のままになっていないか（`TODO_ARCHIVE.md` に移し忘れた完了項目が残っていないか）
6. **`specification/` は基本的に読むだけ**: 実装との差分は `TODO.md`/`TODO_ARCHIVE.md` 側に記録する。設計意図そのものを書き換えたい場合はユーザーに確認してから行う。

## 書き方のトーン

- 既存ドキュメントは日本語・である体/常体混在だが簡潔。過度に丁寧な文体にしない。
- 「なぜその実装を選んだか」「何を発見したか」を一言残す（例: 「〜という偏りを発見し、〜で対処」）。単に「実装した」だけで終わらせない。
- 見出し番号・マイルストーン名（A〜H）は勝手に増やしたり順番を変えたりしない。次のマイルストーンを追加する場合はユーザーと相談する。
