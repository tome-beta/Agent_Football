# 異常検知→原因特定

大量実行で「異常が起きるシード」を絞り込み、そのシードだけをターン単位で再実行してログを追い、原因のコード箇所を特定するまでを一気通貫でやる。統計的な偏りの把握だけなら [[balance-check]]、コードリーディング起点の調査なら [[find-bugs]] を使う。

## 全体の流れ

1. **大量実行で異常シードを絞り込む**
2. **異常シードだけをターン単位で再実行してログを追う**
3. **原因のコード箇所を特定する**
4. **修正 → 再現テストに落とす → 検証する**

一時スクリプトはすべて**プロジェクトルート直下**（`src/` の外）に置き、`scratch_` プレフィックスを付ける。作業が終わったら必ず削除する（コミットに混ぜない）。

## 1. 大量実行で異常シードを絞り込む

`scratch_scan.ts` を書き、`Simulator`（`src/renderer/nullRenderer` の `NullRenderer` 使用）または `createInitialState` + `stepMatch` の手動ループで、最低50〜100シードを連続実行する。各試合について記録する:

- 例外の有無・スタックトレース
- 座標・速度に `NaN`/`Infinity` が出ていないか（`Number.isFinite` でチェック）
- 異常に早い／遅いゴール、同じターンでの連続ゴールなど不自然なタイミング
- `balance-check` で見るような勝敗の偏りも合わせて見てよい

異常が出たシードの一覧（シード番号 + 異常の種類）をコンソールに出力する。異常が1件も出ない場合は、疑わしい条件（特定の `GameConfig` 上書き、特定フェーズなど）を変えて再走査する。

### 「震える」「ジッターする」系の異常（見た目の不自然さ）はスコア統計に出ない

クラッシュ・NaN・スコア偏りと違い、選手が小刻みに振動して見える不具合は勝敗・得点に大きく影響しないことが多く、通常の統計走査では見つからない。目視で「震える」と報告された場合は、選手ごとに `vel`（速度ベクトル）をターンごとに記録し、**直前ターンとの向きがほぼ反転している回数**を数えるとよい:

```ts
function dot(a, b) { return a.x * b.x + a.y * b.y; }
function len(a) { return Math.sqrt(a.x * a.x + a.y * a.y); }

// samples: { turn, vel }[] を選手ごとに集める
let flips = 0;
for (let i = 1; i < samples.length; i++) {
  const prev = samples[i - 1].vel, cur = samples[i].vel;
  const lp = len(prev), lc = len(cur);
  if (lp > 0.5 && lc > 0.5 && dot(prev, cur) / (lp * lc) < -0.3) flips++; // cos(角度) < -0.3 ≈ 108度以上の反転
}
```

flips が多い選手を特定したら、その選手の `pos`/`vel`/`intent.type` をその区間だけ詳細に出力し、位置が2〜3点の間を毎ターン往復していないか確認する。往復していれば、以下のどちらか（あるいは両方）を疑う:

- **目標地点の不連続なジャンプ**: しきい値（`if (dist < range)` のような二値判定）をまたぐたびに目標が固定量だけ跳ぶ実装がないか探す（`markerAvoidRangeFactor`/`markerAvoidStepDistance` で実際に見つかった例あり）。「最寄りの1点だけを基準にする」実装は、僅かな位置変化で「最寄り」の入れ替わりが起きて方向が丸ごと反転しやすい。`applyTeammateRepulsion` のように**範囲内の全員の寄与を合算する**連続的な実装に直すと解消する。
- **到達減速の欠如**: `moveToward` 系の関数が、目標までの距離に関わらず常に最大速度で移動させていないか確認する。目標がわずかに動き続ける状況（ボール追従など）で、1ターンの移動距離が残り距離より長いと毎ターン目標を通り越し、逆方向へ全速力で戻る振動が起きる。`速度上限 = min(最大速度, 残り距離 / dt)` のように到達直前で自動的に減速させると解消する。

## 2. 異常シードだけをターン単位で再実行してログを追う

異常が出たシードを1つ選び、`scratch_repro.ts` で `stepMatch` を1ターンずつ手動で回し、異常が発現する直前〜直後のターンで以下を `console.log` する:

- `state.phase` / `state.phaseTurn` / `state.turn`
- `state.ball`（`pos`/`vel`/`status`/`possessorId`/`lastKickerId`）
- 関係しそうな選手の `pos`/`vel`/`state`

異常発現ターンが特定できたら、そのターン付近だけ `decideAction`/`stepPlayer`/`stepBall`/`resolveBallPossession` などを個別に呼び出し、どの関数呼び出しの前後で値がおかしくなるかを二分探索的に絞り込む。

## 3. 原因のコード箇所を特定する

絞り込めたら該当関数を読み、[[find-bugs]] の「状態のライフサイクル」「境界条件」「呼び出し順序への暗黙の依存」の観点を当てはめて原因を特定する。コードを読むだけで確信が持てない場合は、その関数だけを切り出した最小再現（該当状態を直接セットして1回だけ呼ぶ）を書いて確定させる。

## 4. 修正・後始末

1. 該当箇所を修正する
2. 再現シナリオ（異常シード、または最小再現で使った状態）を `tests/` 配下の恒久的なテストに落とす
3. `verify` スキルで型チェック・全テスト・ヘッドレス実行を通す
4. `scratch_` プレフィックスの一時スクリプトをすべて削除する（`rm`）

## 過去の実績

2026-08-01 のマイルストーンG着手時、balance-check の手順で「キックオフ側がほぼ確実に得点する」偏りが見つかった（`config.ai.positioning` の守備weightが弱すぎたのが原因）。このような「大量実行→偏りに気づく→原因のコード箇所を特定する」流れを定型化したのがこの Skill。

2026-08-14、ユーザーから「試合を見ていて選手が震える」と目視で報告があった。上記の「震える/ジッター系」の速度反転カウント手法でその場から原因調査を始め、`applyTeammateRepulsion`（味方同士の反発）と同じ「最寄り1点だけを基準にする」実装だった `markerAvoidance`（敵マーカー回避）の二値判定と最寄り選択が2つとも不連続の原因だと特定。さらに、それらを連続化してもなお別の震えが残っていたため深掘りし、根本原因は `moveToward` に到達減速がないことだった（目標に近い距離でも常に最大速度で移動するため、毎ターン目標を通り越して逆方向へ戻る振動が起きていた）。統計的な勝敗・得点には表れない種類の不具合で、目視報告が唯一の発見経路だった。
